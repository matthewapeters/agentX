# Context Visualizer — Feature Specification (Working Draft)

**Unit name:** `ContextMeterWidget`
**Status:** Design / Refinement (PRE-01 and PRE-02 completed)
**Last updated:** 2026-04-26
**Revision:** 7 — PRE-02 implementation completed with provider abstraction and startup model metadata store

---

## Purpose

Provide the user with a persistent, at-a-glance view of how much of the LLM's context window is currently consumed and by which categories of content, so they can make informed decisions before and after sending prompts.

---

## 0. Prerequisites

The following prerequisites must exist before the full interactive feature set is considered complete.

| Code | Prerequisite | Why it is required | Linked architecture items |
|------|--------------|--------------------|---------------------------|
| **PRE-01** | **Stable message identity (`message_id`)** on every `Message` | Clone/synthesis lineage (`cloned_from`, `synthesis_of`), row targeting, and deterministic UI actions require stable IDs that are not tied to file paths or list positions. **Status: Complete (2026-04-26).** | **ARCH-17**, **ARCH-15**, Section 14 |
| **PRE-02** | **Dynamic context resizing based on active model selection** | The meter denominator must update when the model changes so percentages and remaining-capacity visuals stay accurate for the selected model's context window. **Status: Complete (2026-04-26).** | **ARCH-08**, **ARCH-09**, **ARCH-10**, **ARCH-05** |

Implementation tracking for PRE-02 is maintained in `docs/context_size_prerequisite_plan.md`.

### 0.1 Dynamic Context Resizing Definition

For this document, "dynamic context resizing" means:

- Fetch context-window size from model metadata (`/api/show`, e.g. `llama.context_length`)
- Preload model capacities at startup into a shared in-memory `ModelMetadataStore`
- Reuse disk cache (`sessions/_model_cache.json`) when model set is unchanged
- Trigger immediate meter redraw after model change so UI percentages reflect the new limit
- Preserve current numerator estimates while denominator updates; never use `parameter_size` as a proxy

## 1. Core Requirements

These items were specified by the user and form the baseline acceptance criteria for the feature.

| Code | Requirement |
|------|-------------|
| **REQ-01** | Display a horizontal color-band meter showing how much of the context window is consumed. |
| **REQ-02** | Distinguish token consumption by category: **Working Memory (WM)**, **Attachments**, **User Prompts**, **Canned / System Prompts**, **Thinking**, and **Agent Response**. |
| **REQ-03** | Each band is proportional to its share of the current `max_tokens` limit for the active LLM. |
| **REQ-04** | ~~Place the widget inside the input area, **to the right of the text input field**, **above the Submit button**.~~ **Superseded by PD-12 StatusTab**: meter is now hosted in the Status tab of the system notebook (right pane). See `docs/ux/03_PANEL_DETAILS.md §PD-12`. |
| **REQ-05** | Recompute and redraw when the user **submits a prompt**. |
| **REQ-06** | Recompute and redraw when the user **enables or disables any context element** (message, attachment, WM fact, etc.). |
| **REQ-07** | Recompute and redraw when **agent streaming finishes** (i.e. after the `DONE` chunk is received, not during streaming). |
| **REQ-08** | The percentage values represent a fraction of the **max tokens setting for the active LLM model**, not a fixed constant. |
| **REQ-09** | Band fill colors represent **data type only** and must remain stable across risk levels. |
| **REQ-10** | Capacity risk is represented by the **meter container border**, not by re-coloring the category bands. Border states: default thin gray, warning thin red at the critical threshold, critical thick red at `>= 100%`. |
| **REQ-11** | The widget must provide color-blind-safe redundancy so meaning is not conveyed by hue alone (text, border weight/state, and optional patterns). |

Initial mapping of GUI categories to `MessageRole` values and other context sources.

| Code | Band Label | Source / Role(s) | Suggested Colour |

## 3. Enrichment Ideas

Proposed enrichments to the baseline requirements. Each is independently discussable.

### 3.1 Visual Enrichments

| Code | Idea | Description |
|------|------|-------------|
| ~~**ENH-01**~~ | ~~Three-tier colour shift~~ | **Removed.** Re-coloring the full meter conflicts with category-color semantics. Capacity risk now uses border state (see ENH-16). |
| **ENH-02** | **Remaining-capacity band** | A trailing pale/dim band always fills the unused portion of the meter so the user can see how much headroom remains. Distinct from disabled content — this represents genuinely unclaimed capacity. Redundant with ENH-05 if that is also accepted, but mutually reinforcing. |
| **ENH-03** | **Overflow hatching** | If the total estimated tokens exceed `max_tokens` (possible before the next trim runs), a red hatched overhang extends beyond the 100% mark rather than silently clipping the meter at full width. |
| ~~**ENH-04**~~ | ~~Disabled-content ghost underlay~~ | **Removed.** The application's design already exposes all historical context elements as re-enableable; there is no unambiguous set of content to call "disabled reserve". The Context Panel is the correct place to reason about toggling individual messages. |
| **ENH-05** | **Token label** | A small text label alongside the meter reading `3 421 / 32 768 tokens` (raw count / model max), with the model name or context window size shown as a tooltip. |
| **ENH-16** | **Capacity-risk border states** | Meter container border indicates risk: **Default** thin gray (`#9ca3af`) when below **80%**, **Warning** thin red (`#CC4444`) from **80%** to `< 100%`, **Critical** thick red (`#FF0000`) at `>= 100%`. Category band colors remain unchanged. |

### 3.2 Interaction Enrichments

| Code | Idea | Description |
|------|------|-------------|
| **ENH-06** | **Hover tooltips on bands** | Hovering over a band shows a small tooltip: `<Role> · ~N tokens (~X%) · M messages`. Notes that the count is an estimate (model-ratio unless tokenizer mode is enabled). |
| **ENH-07** | **Pending-input preview band** | A thin real-time band showing the estimated token cost of the user's *currently-typed-but-not-yet-submitted* text. Updates on every keystroke. Helps users self-regulate before hitting Send. |
| **ENH-08** | **Trim warning badge** | When total exceeds ~90%, add a badge or tooltip reading "Context will be trimmed on next send — oldest turns dropped first". Appears on the meter itself, not as a separate alert. |
| **ENH-09** | **Click-to-navigate** | Clicking a band scrolls the Context Panel to and highlights the first message belonging to that category. |
| **ENH-11** | **Context Panel tab** | A permanent "Context" tab in the display pane shows every enabled context element grouped by role category. Always present; always live. Clicking a meter band focuses this tab at the relevant category. List freezes during streaming and rebuilds atomically on `DONE`. |
| **ENH-12** | **Per-element enable/disable toggle** | Each row in the Context Panel has a toggle. Disabling a row excludes it from the next LLM send and triggers a meter recompute. Non-destructive — the element is retained in session storage. |
| **ENH-13** | **Multi-select + selection action bar** | Rows support checkbox multi-selection. When ≥ 1 row is selected, a selection action bar appears: `N selected · [Disable] [Synthesize] [Clear]`. Bar hides when selection is empty. |
| **ENH-14** | **Synthesize selected elements** | [Synthesize] in the action bar sends selected messages to the LLM with a compression prompt, creates a new `SYNTHESIS`-role message (enabled), disables source rows, and stores `synthesis_of` backreferences. |
| **ENH-15** | **Clone / edit element (inline)** | Each row can be expanded inline to reveal an editable `tk.Text` widget — no modal. Saving creates a clone with edits applied; original is disabled with a `cloned_from` backreference. Discarding restores the collapsed read-only row. |

### 3.3 Architecture / Implementation Ideas

| Code | Idea | Description |
|------|------|-------------|
| **ARCH-01** | **`Context.token_breakdown()`** | Add a method to `Context` returning `dict[str, int]` of estimated token counts keyed by category. The visualizer widget stays purely presentational — all logic lives in the model. |
| **ARCH-02** | **Max tokens from model info** | Retrieve `max_tokens` from `ToolLoopRunner._get_max_tokens()` (which queries the live Ollama model) rather than from the `MAX_TOKENS` constant, so the meter reflects the actual context window of the selected model. |
| **ARCH-03** | **Tag WM SYSTEM message at source** | In `_build_shared_context()`, set a metadata flag (e.g., `msg.metadata["is_working_memory"] = True`) on the generated SYSTEM message so BAND-01 and BAND-02 can be distinguished without string-parsing the content. |
| **ARCH-04** | **`ContextMeterWidget` class** | Implement as a standalone class in `src/agentx/gui/context_meter_widget.py`, following the existing back-reference pattern (stores `self._g = gui_manager`). Tkinter canvas-based rendering for the bands. |
| **ARCH-05** | **Update hook in `IGUIManager`** | Add `update_context_meter()` to the `IGUIManager` protocol so `session.py` can trigger redraws at the three specified events without coupling directly to the widget. |
| **ARCH-06** | **Thread safety** | Redraws must run on the main Tkinter thread. Any post-streaming redraw triggered from the background streaming thread must be scheduled via `root.after(0, ...)`. |

### 8.4 Accessibility Notes

- Colour alone does not convey meaning — each band carries a `BAND-NN` identity that the tooltip confirms.
- Capacity risk must be readable without hue discrimination: border thickness/state, explicit tooltip text, and warning/critical labels are required.
- Pattern overlays (hatching, dots, stripes) are supported to improve category discrimination for color-blind users while preserving existing category assignments.
- Palette choices should preserve luminance contrast between adjacent bands and be reviewed against common color-vision deficiencies (deuteranopia/protanopia).

## 9. Token Counting and the Embedding Question

### 9.1 Clarifying the Terms

**Embedding** and **tokenization** are completely different operations:

| Concept | What it does | Used for |
|---------|-------------|---------|
| **Tokenization** | Splits text into sub-word tokens; counts them | Determining how much of the context window text consumes |
| **Embedding** | Maps text to a high-dimensional numeric vector | Semantic similarity, retrieval, clustering |

Embedding models (e.g., `nomic-embed-text`, `mxbai-embed-large` hosted on Ollama) produce *vectors*, not token counts. They are not a path to more accurate token measurement. **Bundling embedding into this feature would not improve counting accuracy.**

Embedding *could* be relevant to a separate, future "smart context trimming" feature (keep semantically-relevant history, drop irrelevant turns) but that is explicitly out of scope here (Section 6).

### 9.2 Token Counting Options

Four strategies are available, in increasing accuracy and cost order:

| Code | Strategy | Accuracy | Latency | Dependency |
|------|----------|----------|---------|-----------|
| **TOK-01** | `len(content) // 4` (current) | ±30–50% | Zero | None |
| **TOK-02** | Model-family char/token ratios (Llama ≈ 3.5, Mistral ≈ 3.8, Phi ≈ 4.0, default ≈ 4.0) | ±15–25% | Zero | None — ratios baked in |
| **TOK-03** | Ollama `/api/tokenize` endpoint | Exact for the active model | One HTTP round-trip per recompute (~5–20 ms locally) | Ollama ≥ v0.1.29 |
| **TOK-04** | `tiktoken` library | Exact for OpenAI-family models; wrong for others | Near-zero (local BPE) | Extra pip dependency; GPT tokenizers only |

**Current recommendation**: **TOK-02**. Zero latency, no new dependencies, meaningfully better than the current 4-chars-per-token flat rate, works for all Ollama models. Can be upgraded to TOK-03 later via the `ITokenizer` interface already documented in `docs/integration/04_IMPROVEMENT_SUGGESTIONS.md §1.3`.

### 9.3 Model Interface Considerations

The current architecture uses only the **OpenAI-compatible chat endpoint** (`/v1/chat/completions`) via Ollama. No direct Ollama-native endpoints are used for chat.

Switching to Ollama-native endpoints (`/api/chat`) would give access to richer metadata in responses (e.g., `prompt_eval_count`, `eval_count` — exact token counts returned after each completion). However:

- This would require modifying `ToolLoopRunner._iter_llm_chunks()` and the entire streaming pipeline.
- It would break compatibility with non-Ollama OpenAI-compatible backends.
- This is a large, separate change — **not a prerequisite for the meter**.

The pragmatic path is: use TOK-02 for default numerator estimates, and separately fix the denominator (Section 10). Exact token counts from `prompt_eval_count` could be used *retroactively* after each completion to recalibrate — this would be a follow-on enhancement (**ENH-10**: post-completion token calibration).

## 10. Model Responsiveness

### 10.1 The Current Denominator Problem

`max_tokens` is currently derived in `src/agentix/models.py → get_model()`:

```python
max_tokens = parse_parameter_size(model["details"]["parameter_size"])
```

`parameter_size` is the model's *weight count* (e.g., "7B", "32B") — **not the context window length**. A 7B-parameter model can have a context window anywhere from 4 096 to 131 072 tokens depending on its architecture. Using parameter count as a context-window proxy produces wildly inaccurate denominators for the meter.

**Correct source**: Ollama's `/api/show` endpoint returns `model_info["llama.context_length"]` (or the equivalent for non-Llama architectures), which is the actual context window.

```
POST /api/show  { "model": "llama3.2" }
→ { "model_info": { "llama.context_length": 131072 }, ... }
```

This one fix — independent of token-counting strategy — would make REQ-08 ("percentage of max tokens") meaningfully accurate. It is recommended as **ARCH-08**.

### 10.2 Model-Change Event Chain

When the user selects a different model in `ModelSelector`:

```
User selects "qwen3:7b"
  → ModelSelector._on_selection()
  → on_model_change("qwen3:7b")          [existing callback]
  → session.active_model = "qwen3:7b"
  → agentix_adapter.agentix_config.model = "qwen3:7b"
                                          ↑ existing behaviour stops here

  [NEW] → meter_max_tokens_cache = None   ← invalidate cached context window
  [NEW] → session.gui.update_context_meter()   ← trigger redraw with new denominator
```

The new context window is fetched lazily on next redraw via `/api/show`. Until the fetch completes, the meter either shows the previous model's window size (with a stale indicator) or shows "—" for the denominator.

This requires:

- **ARCH-09**: `ContextMeterWidget` holds its own `_cached_max_tokens` (independent of `ToolLoopRunner._max_tokens`) and exposes `invalidate_model_cache()`.
- **ARCH-10**: `session.active_model` setter calls `gui.update_context_meter()` (or a separate `gui.invalidate_meter_model_cache()`) after updating the bridge config.

### 10.3 Different Models, Different Window Sizes — Summary

| Model family | Typical context window | Notes |
|-------------|----------------------|-------|
| Llama 3.2 3B / 8B | 128 000 | `llama.context_length` = 131 072 |
| Mistral 7B (v0.3) | 32 768 | — |
| Qwen3 7B | 32 768 – 131 072 | Varies by variant |
| Gemma 3 | 128 000 | — |
| Phi-3 Mini | 4 096 – 128 000 | Varies by variant |
| `phi4-mini` | 16 384 | — |

The variance is large enough that a wrong denominator would make the meter misleading. This makes ARCH-08 (fetch from `/api/show`) a near-prerequisite for the feature to be trustworthy.

## 12. Context Panel

### 12.1 Purpose and Lifecycle

The Context Panel is a permanent tab in the display pane titled **"Context"**. Created at session start; always navigable; never a modal. It is the management surface for everything the ContextMeterWidget visualizes: the meter shows *what*; the Context Panel shows *why* and lets the user act.

### 12.2 Live Update Behaviour

| Phase | Panel behaviour |
|-------|----------------|
| **Idle** | Full affordances active; rows reflect current `Context.messages` |
| **Streaming** | List frozen at last-computed state; row edits blocked; selection action bar disabled |
| **`DONE` chunk received** | Atomic rebuild from updated `Context.messages`; meter also recomputed simultaneously |
| **Inline edit active** | Edit row open; all other rows read-only; submit button blocked (ARCH-14) |

### 12.3 Row Anatomy

Each row represents one logical context element:

```
┌─[ ]──[▶]────────────────────────────────────────────[●]─┐
│  sel  exp   Role icon · Role name · ~N tokens · X%       │
│             Content preview (first ~80 chars, truncated) │
│  ┌────────────────────────────────────────────────────┐  │  ← expanded only
│  │  editable tk.Text widget                           │  │
│  └────────────────────────────────────────────────────┘  │
│  [Save]  [Discard]                                        │  ← expanded only
└───────────────────────────────────────────────────────────┘
```

- `[ ]` — select checkbox (AFF-15); shows/hides the selection action bar
- `[▶]` / `[▼]` — expand toggle (AFF-12); at most one row expanded at a time
- Role icon + name + estimated tokens + percentage of context window
- Content preview — read-only, truncated; hidden when row is expanded
- `[●]` / `[○]` — enable/disable toggle (AFF-11), right-aligned

### 12.4 Row Visual State Matrix

Six state dimensions can co-occur. Higher priority wins visually:

| Priority | State | Visual treatment |
|----------|-------|-----------------|
| **1** | Streaming (being-written) | Animated pulsing border; all row controls disabled |
| **2** | Expanded (edit active) | Elevated background; editor widget visible; [Save]/[Discard] shown |
| **3** | Selected | Selection highlight tint; checkbox checked |
| **4a** | Synthesis source | Dimmed; italic; annotation `→ synthesised as #<id>`; toggle locked |
| **4b** | Clone source | Dimmed; italic; annotation `→ cloned as #<id>`; toggle locked |
| **5** | Disabled (user-toggled) | Greyed; token count struck through; toggle shows `○` |
| — | Enabled (normal) | Default appearance per BAND colour; toggle shows `●` |

States 4a and 4b are mutually exclusive in practice.

### 12.5 Tkinter Implementation Approach (ARCH-11)

The panel uses a `tk.Text` widget as a scrollable container. Row `tk.Frame` widgets are embedded via `window_create` at sequential text positions. This provides:

- Built-in scrollbar across an arbitrarily long list
- Atomic row insertion (append frame on `DONE` refresh)
- In-place expansion (swap compact frame for expanded frame at same text index)
- Correct tab order within each embedded frame

The `tk.Text` widget itself has `state=DISABLED` for its text layer; only the embedded frame widgets are interactive.

### 12.6 Selection Action Bar (ENH-13)

A `tk.Frame` anchored above the scrollable row list. Hidden when selection count = 0:

```
┌────────────────────────────────────────────────────────────┐
│  3 selected   [Disable]   [Synthesize]   [Clear selection] │
└────────────────────────────────────────────────────────────┘
```

- **[Disable]** (AFF-16): disable all selected rows; clear selection; trigger recompute
- **[Synthesize]** (AFF-17): initiate ENH-14 synthesis flow (§12.7)
- **[Clear selection]** (AFF-18): deselect all; hide bar
- Both action buttons `state=DISABLED` during streaming

### 12.7 Synthesize Flow (ENH-14)

```
User selects N rows → clicks [Synthesize]
  → Action bar: "Synthesising N items…" + spinner
  → Background LLM call: compression prompt + selected message contents
  → On completion:
      a. New SYNTHESIS-role Message created (enabled=True, synthesis_of=[id1, …])
      b. Source rows: enabled=False; visual state = synthesis-source (toggle locked)
      c. Synthesis row inserted at position of last source item in list
      d. Selection cleared; action bar hidden
      e. Meter recomputed
  → User may then expand the synthesis row and edit inline (AFF-12 / AFF-13)
```

**Open (Q-11):** Whether step (b) is gated by a preview/approval step before originals are disabled is a pending decision.

### 12.8 Clone / Edit Flow (ENH-15)

```
User clicks [▶] on any row
  → Row expands; tk.Text editor populated with full message content
  → Submit button disabled (ARCH-14)
  → User edits

  Path A — [Save]:
      a. New Message: same role, edited content, enabled=True, cloned_from=<original_id>
      b. Original: enabled=False; visual state = clone-source (toggle locked)
      c. Row collapses; clone row appears directly below original
      d. Submit re-enabled; meter recomputed

  Path B — [Discard]:
      a. Editor content discarded; row collapses back to read-only preview
      b. No state changes; submit re-enabled
```

### 12.9 Block-Send Behaviour (ARCH-14)

When `ContextPanelWidget.edit_active == True`:

- Submit `Button` → `state=DISABLED`
- Input text area → amber border applied
- Hovering the (disabled) submit button → tooltip: `"Save or discard the open edit in the Context Panel before sending."`
- Interrupt button remains enabled
- `Enter` / `Ctrl+Enter` in input area: no effect

On Save or Discard: `edit_active = False` → submit re-enabled → amber border removed.

## 13. System-Injected Content in the Context Panel

Working Memory and system prompt files are not stored as `Message` objects in `Context.messages` — they are generated or loaded at send-time by `_build_shared_context()`. They require a distinct handling path.

### 13.1 Working Memory (BAND-01)

**Appears as:** A synthetic read-only row at the top of the panel, labelled "⚙ Working Memory". Content preview shows the first ~80 characters of the `<working_memory>` XML block.

**Disable:** Session-level flag `session_config["suppress_working_memory"]`. When `True`, `_build_shared_context()` omits the WM injection. Row shows as disabled; meter recomputes.

**Edit:** Not directly editable in the Context Panel — WM content is managed through the existing WM management UI. The row provides a navigation link to that UI.

**Clone (deferred):** Could snapshot the current WM content as a static `SYSTEM`-role `Message` ("freeze WM at this point in time"). Deferred to a follow-on.

### 13.2 System Prompt Files (BAND-02)

**Appears as:** One synthetic row per loaded system prompt file (e.g., `tool_use.md`, `planner_prompt.md`), labelled with the filename and a `⚙` icon.

**Disable:** Session-level set `session_config["suppressed_system_prompts"]`. Adding a filename suppresses that file's injection for the session. Row shows as disabled; meter recomputes.

**Edit / Clone:** Creates an in-session override — a new `SYSTEM`-role `Message` containing the edited content is stored in `Context.messages`. The file-backed version is added to `suppressed_system_prompts`. The synthetic row is replaced by the real (editable) message row from that point forward.

### 13.3 Dependency on ARCH-03

ARCH-03 (tagging the WM SYSTEM message with `metadata["is_working_memory"]`) is a hard prerequisite for the Context Panel to route BAND-01 vs. BAND-02 rows to the correct disable/edit path. String-parsing the `<working_memory>` block as a fallback is fragile and must not be used.

### 13.4 Visual Differentiation

Synthetic rows (WM and system prompt files) carry a `⚙` icon in the role column to signal they are infrastructure content, not conversation turns. Exact icon or border-colour treatment is open.

## 14. Data Model Changes

### 14.1 Message Schema Additions

Four new fields on the `Message` dataclass (`src/shared/models/message.py`):

| Field | Type | Default | Purpose |
|-------|------|---------|---------|
| `message_id` | `str` | generated UUID | Stable identity for cross-message references and UI operations. Persisted in session JSON and used by clone/synthesis provenance fields. |
| `enabled` | `bool` | `True` | Whether this message is included in the next LLM send. Toggled by ENH-12; also set `False` by ENH-14 (synthesis) and ENH-15 (clone). |
| `cloned_from` | `Optional[str]` | `None` | Message ID of the original this message was cloned from. `None` for non-clones. |
| `synthesis_of` | `Optional[list[str]]` | `None` | Ordered list of Message IDs that were synthesised to create this message. `None` for non-syntheses. |

### 14.2 Session JSON Compatibility

All four fields default to the current implicit behaviour, so existing session files load without migration:

- `message_id=<generated>` — existing messages receive generated stable IDs during load
- `enabled=True` — all existing messages behave as fully enabled
- `cloned_from=None` — no existing messages are clones
- `synthesis_of=None` — no existing messages are syntheses

`Message.from_dict()` must handle missing keys by applying defaults (consistent with the `mime_type` crash fix tracked separately).

### 14.3 Context.token_breakdown() Update (ARCH-01)

`token_breakdown()` must filter to `message.enabled == True` before counting. Disabled messages contribute zero tokens to all bands.

### 14.4 MessageRole Coverage

`MessageRole.SYNTHESIS` already exists in the enum. No new role values are required. Clone and synthesis relationships are tracked via Message fields, not via role.
